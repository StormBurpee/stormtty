# StormTTY: Ghostty engine audit and integration decision

**Audited:** 2026-10-28. **Reference:** `ghostty-org/ghostty` at `46e9dc9a927b2e7e7cba79e6902c176127dbdf2c` (2026-10-27, `config: prevent panic on truncated UTF-8 (#14879)`). Local checkout: `/workspace/shared/ghostty-reference`. No repository implementation, commits, publication, or user-computer access performed.

## Decision

**Use the public `libghostty-vt` C ABI as a pinned terminal-state engine; own the entire Windows application around it.** Do not fork the whole Ghostty GUI, and do not build on `include/ghostty.h`: that header explicitly says it is the macOS-tailored internal embedding API and directs external users to `include/ghostty/` instead.

**Recommended initial route:** C++20 native Windows host, direct HWND, DirectWrite text services, D3D11 composition, and a deliberately narrow C++ RAII adapter around a commit-pinned Zig-built `libghostty-vt`. A Direct2D correctness renderer can precede or back up the batched glyph-atlas renderer. One workspace swapchain per window should composite all visible terminal panes. This is a source-supported integration-risk choice, **not a measured claim that C++ is faster than Rust or .NET**.

Native WinUI/C++WinRT chrome is a later evaluated option, not a prerequisite for the first terminal slice. A fully custom HWND shell means we own accessibility, IME/TSF integration, focus traversal, title-bar hit testing, snapping, and control behavior—not just drawing pretty pixels. Both options must meet the same acceptance gates.

## Exact engine boundary and source map

All paths below refer to the audited commit, not moving `main`. Public entry points are [`include/ghostty/vt.h`](https://github.com/ghostty-org/ghostty/blob/46e9dc9a927b2e7e7cba79e6902c176127dbdf2c/include/ghostty/vt.h), `src/terminal/c/main.zig`, and `src/lib_vt.zig`. **The API explicitly warns of breaking changes; `0.1.0` build metadata is not a stability guarantee.**

- **Lifecycle/VT/options:** `include/ghostty/vt/terminal.h`; `ghostty_terminal_new/free`, `ghostty_terminal_vt_write`, `ghostty_terminal_resize`, `ghostty_terminal_set/get`. `ghostty_terminal_resize` receives both grid and cell-pixel geometry.
- **Render data:** `include/ghostty/vt/render.h`, `src/terminal/render.zig`, `example/c-vt-render/src/main.c`. This is renderable state, **not a renderer, framebuffer, native control, font engine, or GPU surface**. Ghostty's own `src/renderer.zig` selects Metal/OpenGL and is outside this library; it is not a reusable DirectX backend.
- **Input:** `include/ghostty/vt/key/{event,encoder}.h`, `mouse/{event,encoder}.h`, `focus.h`, `paste.h`; examples `c-vt-encode-key`, `c-vt-encode-mouse`, `c-vt-paste`. Use encoder `setopt_from_terminal` to follow negotiated modes, rather than hard-coding ANSI or always enabling Kitty keys.
- **Selection/search:** `selection.h`, `grid_ref.h`, `grid_ref_tracked.h`, `search.h`, `formatter.h`; examples `c-vt-selection`, `c-vt-selection-gesture`, `c-vt-search`, `c-vt-grid-ref-tracked`. Search is byte-exact except ASCII-case-insensitive letters, **not full Unicode-folding or regex search**.
- **Images:** `kitty_graphics.h`, `sys.h`, `src/terminal/kitty/graphics_{exec,storage}.zig`, `example/c-vt-kitty-graphics/src/main.c`.
- **Persistence:** `snapshot.h`, `src/terminal/snapshot/main.zig`, `example/c-vt-snapshot`. Snapshot format v1 explicitly lacks a binary-compatibility guarantee. It restores terminal state, not an OS process or live shell connection.
- **Windows reference, not public ABI:** `src/pty.zig` has `WindowsPty` with `CreatePseudoConsole`/`ResizePseudoConsole`; `src/termio/Exec.zig` has Windows reader/process handling. These are useful reference code, not functionality exported by libghostty-vt.
- **Configuration:** library options in `terminal.h`, feature gates in `src/terminal/build_options.zig`; full application configuration in `src/config/Config.zig` is outside the public engine contract. Do not make Ghostty's full app config parser our product schema.

## Critical integration rules

### Rendering and ownership

1. **One serialized owner per terminal.** Effects run synchronously during VT writes. Never re-enter `vt_write` from an effect, block on the UI thread, or hold a terminal lock during GPU work. Queue short copied events; preserve protocol-response byte ordering.
2. `GhosttyRenderState` is **updated in place**, not immutable. Borrowed row/cell views expire on its next update. Publish our own immutable `RenderFrame` or ownership-safe double-buffered frame; never keep borrowed views after the producer reuses state.
3. Two-phase `ghostty_render_state_begin_update`/`end_update` confines terminal-exclusive access to `begin`. Always finish `end` before reading. Reset dirty state only after successfully consuming/rendering the corresponding frame using `ghostty_render_state_clean` (both global and row dirtiness).
4. Images are an exception to snapshot ownership: render state stores **placement metadata, not copied pixels**. Copy newly needed image pixels while terminal ownership/lock is held, then upload outside it. Kitty handles expire at the next mutating terminal operation. Cache textures by image generation, not dimensions or ID alone. For the first correct implementation, complete the update and pixel copies under the session actor's ownership; optimize into two phases later. Releasing terminal ownership between placement capture and pixel lookup can otherwise pair an old placement generation with new pixels.
5. Use stable row IDs and dirty rows for shaping caches; overscan supports smooth scroll. Raw bulk cells exist, but bit positions are explicitly not ABI-protected: use C getters or the `ghostty_type_json` ABI manifest, never copied bit masks. Bindings should batch per-row data rather than cross a managed boundary per cell.

### Input, resize, and animation

- **ConPTY-specific setting:** set `GHOSTTY_TERMINAL_OPT_RESIZE_PULL_SCROLLBACK` to false. `terminal.h` explicitly names ConPTY as the reason: its own no-scrollback screen model otherwise disagrees with the terminal after resizing. Resize the engine and ConPTY coherently while panes drag; verify wide-character/reflow/cursor behavior under output.
- **DEC private mode 2026 is not automatic at the render call.** Register `GHOSTTY_TERMINAL_OPT_RENDER_HOLD`, capture the frozen frame when a hold begins, avoid updating that render state until it ends, and expire stuck holds with a bounded timer (header suggests one second). Merely calling `render_state_update` every frame produces partial TUI frames.
- Key API accepts normalized physical key, press/repeat/release, modifiers/consumed modifiers, UTF-8 text, unshifted codepoint, and composing flag. It **does not implement Windows TSF, keyboard layout translation, composition UI or candidate positioning**. Keep preedit local; send committed text once; test dead keys, AltGr, surrogate pairs, CJK IME, Ctrl chords, and shortcut suppression during composition.
- Mouse API includes X10/normal/button/any-event tracking and X10/UTF8/SGR/URXVT/SGR-pixel encodings. Supply current cell/pixel/padding geometry; separately own wheel accumulation, touchpad behavior, captured drags, and selection-vs-application reporting policy.
- Paste helpers implement bracketed paste and unsafe-paste rejection. `ghostty_terminal_paste` writes ordered chunks through the PTY callback. Keep a stable payload across our confirmation flow so the user authorizes the bytes actually sent. Distinguish clipboard paste from IME/scripted text insertion.

### Graphics scope and security

- Kitty graphics must be enabled in the build **and** given a nonzero runtime image-storage budget. PNG requires the process-global `GHOSTTY_SYS_OPT_DECODE_PNG` callback installed at startup. Allocate the returned RGBA buffer using the provided Ghostty allocator; impose dimension/decoded-byte checks before allocating/decoding.
- Public render placements cover fixed, Unicode-placeholder and relative images, source/destination rectangles, three compositing layers and z-index. No second draw pass from the storage placement iterator: that duplicates images already in render state.
- Animation is caller-driven via `ghostty_kitty_graphics_animation_tick`; use its next deadline, cap to display frame cadence, and sleep when nothing animates. No always-running idle animation poller.
- Keep file/temp-file/shared-memory graphics media disabled initially; direct transmissions suffice for the first secure slice. Budget image/APC/clipboard/scrollback memory, queue depth and work per frame. Treat terminal OSC titles/URIs/clipboard requests as untrusted data.
- No SIXEL implementation was found in the audited terminal tree; only the device-attribute capability constant. Do not advertise SIXEL, iTerm image support, or a universal graphics story based on that enum.
- **Engine support is not end-to-end support.** ConPTY can mediate the byte stream. Prove Kitty/OSC/2026 behavior through actual Windows and WSL/SSH launch paths before advertising it. Ink/React TUIs are client processes emitting terminal sequences; StormTTY does not need a React runtime to render them.

## Toolchain and bindings choice

| Route | Source-backed integration assessment | Decision |
|---|---|---|
| C++20 + C ABI + MSVC/Windows SDK | In-tree C/C++ examples, CMake wrapper/imported targets and native Windows CMake CI; direct Windows/DirectX/TSF/UIA APIs; RAII owns opaque handles and borrowed views | **Lowest integration novelty; recommended**. Counter memory/concurrency risk with ownership discipline, sanitizers where supported, fuzzing and safe abstractions |
| Rust + C ABI + Windows APIs | Ordinary C ABI makes it feasible; opaque handles suit a small unsafe module with safe owner-bound wrappers. No in-tree Rust binding found. Still requires Zig to build the engine and Windows-specific UI/IME work | Strong alternative if team Rust competence outweighs added binding/toolchain work; do not import an unpinned third-party binding as architecture |
| Zig host + Zig module | `src/lib_vt.zig` and Zig examples expose direct integration, avoiding C FFI. Also couples product to unstable Zig and Ghostty internal/public Zig APIs; no shipped Windows GUI runtime to reuse | Good for isolated engine experiments, not the default Windows shell decision |
| .NET/C# + P/Invoke | C ABI can be called, but no in-tree C# binding found. Must handle C `bool`, `size_t`, enum/sized-struct layouts, allocator ownership, pinned callbacks and native lifetime. Avoid per-cell P/Invoke and GC ownership of borrowed views | Viable native-shell option with native renderer/adapter; **not inherently slow**, but more interop surface than C++ for this first slice |

Microsoft documents native C++ and C# support in [Windows App SDK](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/). If using WinUI3, its [SwapChainPanel documentation](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.swapchainpanel) says it does not support transparency/Acrylic backdrop sampling and recommends no more than four simultaneously updated swapchains. Therefore use a single opaque terminal workspace surface, with premium material effects in surrounding chrome—not one swapchain per pane. DPI composition-scale changes and focus routing require explicit handling.

### Build facts—not assumptions

- `build.zig.zon` requires **Zig 0.17.0**; `src/build/zig.zig` enforces the same major/minor with patch >= required. Do not install a generic “latest Zig” and assume compatibility.
- `zig build -Demit-lib-vt` emits shared and static libraries plus headers. Windows names: `bin/ghostty-vt.dll`, `lib/ghostty-vt.lib` (DLL import), `lib/ghostty-vt-static.lib`. Static consumers define `GHOSTTY_STATIC`; system links include `ntdll` and `kernel32`.
- CMake >=3.19 wrapper at `CMakeLists.txt`; `dist/cmake/README.md`; targets `ghostty-vt` and `ghostty-vt-static`. Replace the examples' `GIT_TAG main` with the audited exact commit. Source-fetch dependencies remain required even when runtime linkage is small. `-Demit-lib-vt` disables executable/docs/macOS app/xcframework defaults; it does not accidentally install the full app. Use it on test invocations too.
- Native Windows jobs in `.github/workflows/test.yml:314-342,939-990` build CMake examples, run `test-lib-vt`, build the libraries, exercise static linking and execute a dynamically linked effects example. This is evidence of intended coverage, **not a claim we saw a passing CI run for this commit**.
- Linux cross-build matrix includes `x86_64-windows-gnu`; its `x86_64-windows-msvc` entry remains commented out because MSVC headers are not located there. A MinGW PE build is not evidence of MSVC or Windows runtime correctness. `src/build/Config.zig:105-116` defaults an unspecified Windows ABI to MSVC, explicitly warning that GNU-generated COFF compiler-runtime objects can cause MSVC `LNK1143`; do not reuse the GNU artifact as a proven MSVC dependency.
- SIMD defaults on; it adds libc/build dependencies (Highway/simdutf). `-Dsimd=false` is useful to isolate linking, not a default performance configuration. There is documentation drift: CMake comments say Windows SIMD archives are unbundled, but current `GhosttyLibVt.zig` + `CombineArchivesStep.zig` combine vendored archives on Windows too. Verify real artifact contents and native MSVC linking rather than relying on that comment.
- Library feature switches can remove exports. Keep needed features enabled and assert build metadata/capabilities at startup. `src/terminal/build_options.zig` actually enables Kitty independent of Oniguruma (an earlier comment is stale); freestanding targets disable Kitty. A WASM demo is not a valid substitute for the native graphics gate.

**Already passed, read-only here:** GCC C11 and G++ C++20 umbrella-header syntax checks with `-Wall -Wextra -Werror -DGHOSTTY_STATIC`; C syntax checks of ten examples: stream, render, search, selection, selection-gesture, encode-key, encode-mouse, effects, kitty-graphics, snapshot. This validates header/example syntax only—not linkage, ABI on Windows, behavior, or speed. Reference `git status --porcelain` remained empty.

**In progress, owned by the parent task (last report 00:25 UTC):** it subsequently installed official Zig 0.17.0 (reported SHA256 verified) at `/workspace/shared/toolchains/zig-x86_64-linux-0.17.0/zig`; this agent independently confirmed `zig version` prints `0.17.0`. Parent also reports workspace-local CMake 4.4.4 and Ninja installed. Parent launched `build -Demit-lib-vt -Doptimize=ReleaseFast` with workspace-local caches/output; Zig HTTP connections closed for three dependency downloads, and parent is retrying transport via curl plus local `zig fetch` with dependency hashes verified. This is not an access denial or a compile result. No completed link/runtime result was available when this memo was handed off. Rust, .NET and Windows execution were unavailable at the initial audit. This agent did not install tools or start a competing build.

1. **Reproducible Linux engine smoke** in an authorized writable build copy/cache: pin Zig 0.17.0 and dependency hashes; run `zig build -Demit-lib-vt -Doptimize=ReleaseSafe`, `zig build test-lib-vt -Demit-lib-vt`, and `zig build test-lib-vt-schema -Demit-lib-vt`. Run actual stream/render/effects/input/search/graphics examples. Record emitted build metadata, licenses, and ABI manifest. Zig 0.17.0's installed `lib/compiler/Maker/ScannedConfig.zig` confirms `--fetch=needed` fetches the needed dependency tree and exits; avoid `--fetch=all` unless deliberately caching all lazy GUI dependencies. `--system <pkgdir>` disables fetches **and enables system integrations**; do not use it as a blind offline flag. Keep explicit vendored integration choices/cache paths in reproducible builds.
2. **Windows-format compile smoke:** `zig build -Demit-lib-vt -Dtarget=x86_64-windows-gnu -Doptimize=ReleaseSafe`; `zig build test-lib-vt-build -Demit-lib-vt -Dtarget=x86_64-windows-gnu`; use `example/c-vt-cmake-cross` as the CMake cross consumer. Exit criterion: PE artifacts and symbols verified, explicitly compile-only.
3. **Native Windows/MSVC gate:** Windows SDK + MSVC + Zig 0.17.0; build native shared/static libraries; reproduce `example/c-vt-cmake` and `c-vt-cmake-static`; run examples directly from a clean deployment folder to catch missing DLL/CRT dependencies. Test SIMD both off (diagnostic baseline) and on (shipping candidate); inspect exports/imports and allocator crossing. Add ARM64 separately; existing audited matrix does not prove Windows ARM64 runtime coverage.
4. **Minimal owned vertical slice:** one native window, one ConPTY child, one VT instance, one renderer, bidirectional query/input callbacks, correct lifecycle and resize. Exit only when real Windows output, keystrokes, paste, IME, alternate screen, selection, DPI and device-loss tests pass. No tabs or polished chrome can substitute for this.
5. **Compatibility/performance gate before committing architecture:** real Ink fixture apps plus editor/multiplexer fixtures; rapid resize, wrapped Unicode, queries, 2026 partial-output hold and stuck hold; Kitty PNG/direct RGBA/chunking/animation/placeholders through intended transports; idle CPU and input-to-present p50/p95/p99; flood-output fairness and memory bounds. Do not quote performance without a measured baseline.

Failure classes to diagnose explicitly: wrong Zig minor; unavailable dependency downloads; native MSVC SDK/CRT discovery vs GNU cross ABI; static/DLL import-library name collision; missing SIMD/NT libraries; current Windows sanitizer/stack-protector workarounds; DLL search/deployment; C `bool`/sized-struct mismatch in bindings; freeing Ghostty buffers with host `free`; borrowed data after mutation; incorrect synchronized-output handling; ConPTY resize mismatch; ignored effects/no terminal query responses; PNG decoder missing; zero cell size/no images; graphics bytes not reaching the emulator; high-cost FFI per cell; blocked UI from synchronous callbacks. Also test build paths containing spaces: `src/build/combine_archives.zig` constructs MRI archive paths without quoting—potential integration hazard, not a confirmed failure.

## Bottom line

Ghostty is a credible, unusually complete **terminal semantics engine** for StormTTY, including real reusable graphics and input machinery. The biggest unsolved work is not ANSI parsing: it is Windows transport correctness, native input/accessibility, text/GPU rendering, resource scheduling, and a polished, trustworthy workspace shell. Prove that one-window vertical slice on Windows before spending effort on chrome or claiming compatibility/performance.
